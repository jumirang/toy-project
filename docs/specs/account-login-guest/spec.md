# 계정과 둘러보기: 이메일 가입·로그인, 계정별 관심 기업과 입력값, 가입 없이 둘러보기

연결된 출처:
- [PRODUCT.md](../../../PRODUCT.md): 앱 전체 전제. 출시된 실적 캘린더에 계정과 둘러보기를 더한다.
- [GLOSSARY.md](../../../GLOSSARY.md): 관심 기업, 기본 기업, 둘러보기, 공통 데이터, 계정별 데이터의 뜻.
- [data-ownership](../../decisions/data-ownership.md): 계정별 데이터와 공통 데이터의 경계, 갱신 권한, 둘러보기 범위, 기본 기업. 데이터 소유와 접근 규칙은 이 계약을 따른다.
- [market-data-sources](../../decisions/market-data-sources.md): 실적, 주가, 뉴스, 컨센서스의 출처와 해석. 이 스펙은 바꾸지 않는다.
- [ui-composition](../../decisions/ui-composition.md): 로그인·가입 화면, 둘러보기 안내, 계정 메뉴는 공식 shadcn component로 구성한다.
- [dependency-versions](../../decisions/dependency-versions.md): 의존성을 추가할 때의 버전 기준.

## 사용자에게 보이는 결과

1. 로그아웃 상태로 들어오면 로그인 화면이 보이고, 여기서 `가입`, `로그인`, `가입 없이 둘러보기` 중 하나를 고른다. 가입과 로그인은 이메일과 비밀번호로 한다.
2. 가입하면 곧바로 로그인된 상태가 되고, 삼성전자와 SK하이닉스가 관심 기업으로 담긴 지금의 캘린더 화면이 보인다. 두 기업을 지우면 다시 생기지 않는다.
3. `가입 없이 둘러보기`를 누르면 삼성전자와 SK하이닉스의 캘린더와 상세가 읽기 전용으로 보인다. 관심 기업 추가·삭제, 컨센서스·기업 설명·예정일 수정, 전체 갱신과 기업별 갱신을 누르면 데이터는 바뀌지 않고 가입 안내가 나온다.
4. 로그인한 사용자의 관심 기업 목록, 고친 컨센서스 평균·최저·최고, 기업 설명, 고친 예정일은 그 계정에만 보인다.
5. 로그인한 사용자가 갱신하면 그 기업의 실적, 주가, 뉴스, 자동 추출 컨센서스가 최신으로 바뀌고, 같은 기업을 보는 다른 계정과 둘러보기에도 반영된다.
6. 로그인 상태에서는 어디서나 로그아웃할 수 있고, 로그아웃하면 로그인 화면으로 돌아간다.

## 승인된 범위

- 이메일/비밀번호 가입·로그인·로그아웃과 인증 상태에 따른 화면 분기
- 둘러보기: 기본 기업 둘의 읽기 전용 캘린더와 상세, 쓰기 동작 시 가입 안내
- 가입 직후 기본 기업 둘을 관심 기업으로 담기
- 관심 기업 목록과 사용자 입력값(컨센서스 평균·최저·최고, 기업 설명, 예정일)의 계정별 보관
- 공통 데이터 읽기는 누구나, 쓰기(갱신)는 로그인한 사용자만 하도록 접근 권한 정리
- 기존 데이터 정리: 수집한 공통 데이터는 남기고, 주인 없는 직접 입력값과 기존 관심 기업 목록은 버린다

## 수용 기준

실행 중인 앱을 브라우저로 열어 확인한다. 외부 API와 Supabase는 실제 키로 호출한다. 기존 실적 캘린더의 동작(캘린더, 상세, 컨센서스 추출, 주가 반응, PER/PBR 밴드, 뉴스, 갱신 진행·실패 표시, 390px 한 열 배치)은 로그인한 계정에서 그대로 유지된다.

- AC1. 로그아웃 상태로 앱의 어느 주소를 열어도 로그인 화면이 보이고, 그 화면에 `가입`, `로그인`, `가입 없이 둘러보기`가 있다.
- AC2. 새 이메일로 가입하면 로그인 화면이나 확인 안내를 거치지 않고 로그인된 상태가 되며, 관심 기업 목록에 삼성전자와 SK하이닉스가 들어 있다. 둘을 지운 뒤 로그아웃하고 다시 로그인해도 다시 생기지 않는다.
- AC3. 잘못된 비밀번호로 로그인하면 로그인되지 않고 실패했다는 안내가 보이며, 이미 가입된 이메일로 가입하면 가입되지 않고 안내가 보인다.
- AC4. `가입 없이 둘러보기`로 들어가면 삼성전자와 SK하이닉스의 캘린더와 상세(실적과 컨센서스, 차이 비율, 발표 후 주가 변동률, 과거 반응 표, PER/PBR 밴드, 뉴스)가 로그인 없이 보이고, 이 두 기업 외의 기업은 목록에 나오지 않는다.
- AC5. 둘러보기에서 관심 기업 추가·삭제, 컨센서스·기업 설명·예정일 수정, 전체 갱신과 기업별 갱신의 입구를 누르면 데이터가 바뀌지 않고 가입 링크가 있는 가입 안내가 나온다.
- AC6. 둘러보기에서 아무도 갱신하지 않았어도 삼성전자와 SK하이닉스의 과거 발표일과 상세가 비어 있지 않다.
- AC7. 계정 A가 관심 기업을 추가·삭제하거나 컨센서스·기업 설명·예정일을 고쳐도, 계정 B와 둘러보기에는 바뀌지 않는다. 계정 A가 고친 컨센서스는 A에게 "직접 수정"으로 보이고, B와 둘러보기에는 자동 추출 값(또는 빈칸)으로 보인다.
- AC8. 로그아웃 상태에서 계정별 데이터를 읽거나 쓰는 요청, 공통 데이터를 쓰는 요청은 데이터베이스에서 거부된다.
- AC9. 계정 A가 갱신해 공통 데이터가 바뀌면, 계정 B의 같은 기업과 둘러보기의 같은 기업에 갱신된 값이 보인다. 계정 A가 고친 값은 갱신으로 덮어써지지 않는다.
- AC10. 로그인 상태에서 둘러보기 주소를 열면 내 계정 화면으로 이동하고, `로그아웃`을 누르면 로그인 화면으로 돌아가며 이후 계정 화면에 접근할 수 없다.
- AC11. 계정 기능 적용 뒤, 기존에 입력돼 있던 직접 수정 컨센서스·기업 설명·고친 예정일은 어느 계정과 둘러보기에도 보이지 않고, 수집한 실적·주가·뉴스·자동 추출 컨센서스는 그대로 보인다.
- AC12. 매수·매도를 권하거나 신호를 표시하는 문구가 새 화면(로그인, 가입 안내)에도 없다.

## 확정된 제약과 근거

- 가입과 로그인은 이메일/비밀번호 하나로 하고, 인증과 데이터 보관은 Supabase를 쓴다. 사용자가 가입·로그인 기반 접근을 요청했다. (사용자 확정)
- 계정별 데이터와 공통 데이터의 경계, 갱신 권한, 둘러보기 범위, 기본 기업 규칙은 [data-ownership](../../decisions/data-ownership.md)을 따른다. (사용자 확정)
- 둘러보기는 기본 기업 둘의 상세까지 읽기 전용으로 보여 준다. (사용자 확정)
- 가입 직후 기본 기업 둘을 담고, 지우면 다시 생기지 않는다. (사용자 확정)
- 기존의 주인 없는 직접 입력값과 관심 기업 목록은 버리고, 수집한 공통 데이터는 남긴다. (사용자 확정)
- Supabase 작업은 `AGENTS.md`의 "Supabase 최신 문서" 지시와 설치된 공식 스킬을 따른다.
- 판단 재료만 보여 주고 매수·매도 신호를 내지 않는다. (PRODUCT.md 경계)

## 가정 (바꿀 수 있음)

- 이메일 인증은 끈다. 가입하면 바로 로그인된다.
- 로그인 상태에서 둘러보기 주소를 열면 내 계정 화면으로 보낸다.
- 로그인·가입 화면, 가입 안내, 계정 메뉴의 문구와 배치는 구현이 정한다. 승인된 프로토타입은 없다.
- 상장사 검색 목록(국내 상장사 전체)은 공통 데이터로 두고, 로그인한 사용자만 검색·추가한다.
- 상단의 마지막 갱신 시각은 지금처럼 누군가의 `전체 갱신`이 끝난 시각이다. 기업별 시각은 관심 기업 관리에서 보인다.

## 범위 밖과 이유

- 소셜 로그인, 비밀번호 재설정, 이메일 변경, 계정 삭제, 프로필 화면: 이번 요청이 아니다.
- 목록 공유, 값 공동 편집: 계정별 데이터 결정에 따라 하지 않는다.
- 자동 예약 갱신과 서버 배포: data-ownership의 다시 열 조건에 맡긴다.
- 실적 캘린더 화면 구성과 데이터 출처 변경: 이 스펙은 접근만 바꾼다.
- 보안 하드닝, 엣지케이스·성능 방어: AGENTS.md 검증·리뷰 예산.

## 남은 위험

- 둘러보기 데이터는 로그인한 누군가가 갱신해야 최신이 된다. 아무도 갱신하지 않으면 오래된 값이 보인다.
- 가입이 열려 있어 누구나 계정을 만들 수 있고, 갱신은 외부 API 호출 한도를 쓴다.
- 계정별로 고친 컨센서스는 계정마다 따로 입력해야 해서 입력 부담이 커진다.
- 로그인·가입 화면은 승인된 프로토타입 없이 구현된다. 화면이 기대와 다르면 구현 뒤에 고친다.

## Setup before implementation

- Supabase Auth의 이메일 가입 허용과 이메일 확인 끄기 — 가입 즉시 로그인 — 완료 조건: 앱 밖에서 Supabase Auth 가입 API(`POST <Project URL>/auth/v1/signup`)를 새 이메일로 직접 호출하면 응답에 세션(`access_token`)이 들어 있다.
